# Whole source budgets and scoped financial reads

This DP-02-06 package changes source selection and overload behavior relative to baseline `03f16300f36dabf7930eef2de8ae7690e48feb89`. [PR #21](https://github.com/Cenn0/FirstBlick/pull/21) identifies the final changed revision and its CI evidence. It does not complete the original roadmap task.

## Source contract

[`EntitySources.Read`](../src/FirstBlick.Infrastructure/Persistence/EntitySources.cs) reads a complete source set for an explicit tenant and registered entity kind. It enforces **10,000 records and 12 MiB of PostgreSQL JSONB text per read**, inclusive of both limits. Archived rows are excluded unless the internal caller explicitly includes them for retained maintenance invariants. There is no request option to raise either limit.

Tenant/kind/archive, retained target relationships and optional unique keys filter the set **before** budgeting. PostgreSQL window aggregates, conditional JSON projection and result limiting execute in one statement. If either budget is exceeded, the result contains bounded metadata and null payloads; the reader throws before deserialization. It never returns the first 10,000 records as a usable partial history. A matching source is returned once even if two target relationships match it.

The reader checks tenant, kind, identifier, revision and archived state against each deserialized body. A selected relationship must also exist in the body's references; a requested unique key must match its body-derived projection. The financial adapter additionally calls each entity's domain validation. This catches inconsistent retained metadata or stale selected links; it is not a complete repair or integrity audit of all missing/corrupt database links.

| Caller | Source selection | Failure code family |
| --- | --- | --- |
| `EntityStore.All<T>` | Active records of one tenant/kind; record policies use explicit owner/project selectors | `source_budget`, `source_metadata` |
| Project/contract maintenance validation | Related maintenance visits, including retained archived history | `source_budget`, `source_metadata`, `source_reference` |
| Financial histories | Complete retained relationships for the current order, original invoice, supplier invoice or bank transaction | `financial_source_budget`, `financial_source_metadata`, `financial_source_reference` |
| Bank import replay | At most 500 requested account/external-ID keys, using the existing unique index | `financial_source_budget`, `financial_source_metadata`, `financial_source_key` |

These domain errors use the existing HTTP 400 problem-details path. The existing bank-import content conflict remains HTTP 409 `idempotency_conflict`. Authorization, tenant locking, current revision checks and command receipts retain their existing roles. A failed mutating command must not post a successful receipt, audit event or payment.

## Financial completeness

[`FinancialSources`](../src/FirstBlick.Api/FinancialSources.cs) selects the union of **invoice allocations and bank allocations** when reconciling a customer or supplier payment. Invoice allocations include other bank transactions needed for the invoice balance. Bank allocations include other invoices and both original and returned transaction references needed for shared bank capacity. Customer and supplier allocations are both consulted. Returns therefore continue consuming their original bank entry and the linked return entry; a chargeback does not free the original receipt for reuse.

Invoice credits and supplier credits are selected through the corresponding original-invoice link. Reversals consult both customer and supplier allocations on the selected return transaction. Ordinary bank imports only read the requested external identifiers for the specified account. Repeating an import preserves its source digest check; unrelated history is not deserialized.

## Remaining limits and operations

RecordPolicy now selects active account-linked employees, directly mentored staff, participating training records, personal time/diary/form/preference rows, uncancelled own assignments and assigned-project work **in PostgreSQL before budgeting and JSON projection**. Assigned tasks outside a worker's project list retain their prior visibility; they do not grant access to the whole project. Trainers retain historical training-participant visibility. Neither selectors nor identifiers originate as SQL from an HTTP request.

All `EntitySources.Read` calls within one scoped `FirstBlickDbContext` additionally share **10,000 materialized rows / 12 MiB**. Repeated reads consume work again; this is a workload budget, not a count of distinct business records. Each SQL statement uses the remaining budget in its conditional payload projection. A rejected aggregate source returns null JSON payloads and raises HTTP 400 `source_request_budget` before deserialization. New scopes start with a fresh budget. This replaces discovery's separate whole-tenant pre-count; ordinary resource policy and discovery now use the same selection and accounting.

The shared budget covers this source reader and its store/financial callers. It does not cover every raw SQL, document, single-record, export or worker query. A universal request/workflow resource budget, representative indexing/latency/volume tests and a complete global search index remain work. SQL still evaluates matching rows and JSON predicates to calculate totals; application materialization bounds are not database CPU/I/O/temporary-storage limits.

`RecordPolicySelectionApiTests` adds real-HTTP and PostgreSQL cases for oversized irrelevant tenant sets, exact own/project/task visibility, foreign-tenant isolation, immediate assignment/deactivation revocation, direct trainer relationships, retained report participants, cumulative record/byte rejection before invalid bodies are deserialized, and scoped reset. Its independent budget-boundary case checks inclusive limits and unchanged accounting after rejection. The new local build passes with no warnings; 601 core and 20 database-independent API cases pass. The **318 local PostgreSQL skips are not passes**. The client has 486 passing tests and a successful production build. Mandatory PostgreSQL/browser/container/standards checks must pass at the final PR revision before merge. No exhaustive security scan or business acceptance is claimed.

An operator seeing a source-budget error must retain the complete history and investigate source selection and volume. Arbitrary deletion, truncation or a raised limit is not a safe reconciliation procedure. ## Scoped mutation invariants

Graph validation now reads retained relationships for the candidate building, project, purchase order, employee, material or acceptance project instead of whole tenant kinds. This includes customer/roof/measurement/technical-result invariants, converted material demands, employee/equipment planning conflicts, approved absences, time overlaps, stock reservations and all project defects. The dedicated material-reserve endpoint uses the same material-scoped history as generic reservation creation.

A live planning candidate consults both the employee's assignments and assignments for up to 100 equipment items. These are two bounded source reads, so the existing 100-target source limit is retained even when a candidate also has an employee. The domain-rule input deduplicates shared assignments; actual repeated materialization still consumes the common workload budget. Cancellation releases a slot without loading conflict histories; requested/rejected/cancelled absences likewise do not need approved-absence conflict sources. Existing domain rules continue checking cross-employee equipment collisions, interval boundaries and all relevant own-project/material history.

Source relationships remain tenant-qualified database links maintained by `EntityStore.Save`, with source metadata and retained body-reference checks. This optimization assumes those persisted links are complete; it does not audit or repair missing links in a manually modified database. Unrelated corrupt/unlinked rows are not materialized. Complete relevant histories exceeding the source/workload limits still fail closed; no truncated stock, defect or conflict decision is used.

`GraphSourceSelectionApiTests` adds five mandatory PostgreSQL/HTTP regressions with more than 10,000 unrelated rows: own time conflict and adjacent work with rollback, retained quote/customer invariants, both material reservation paths and overbooking refusal, acceptance reservations for unresolved own-project defects, and cross-employee equipment conflict/cancellation. The local build and 601 core / 20 independent API cases pass; the 323 PostgreSQL cases remain locally skipped and must pass in CI. Client code is unchanged from the 486-case passing client run. Direct stock count/transfer/return queries and other specialized workflows still need separate resource/selection qualification.
